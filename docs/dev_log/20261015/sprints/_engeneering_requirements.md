# Engineering requirements — oxid-fe-core / oxid-fe-user

**Date:** 2026-10-15 · Binding for **every sprint** in this folder. A sprint doc references this file
instead of repeating the principles. Adapted for the frontend stack (Vue 3 / TypeScript / Vite) from the
payment-base convention (`payment-base/docs/dev_log/20260903/sprints/_engeneering_requirements.md`).

## Core requirements

| Principle | Application here |
|-----------|------------------|
| **TDD** | Failing test first, always. A store, composable, guard or client method exists only because a Vitest test demanded it; a user-visible flow (login, add to cart, pay, address edit) is not done until a Playwright test drives it in the browser. Bug fix = failing reproduction test first, then the fix. |
| **SOLID** | *SRP:* one module, one job — the `GraphqlClient` transports, it never knows routes; the `PluginRegistry` registers, it never renders; a view renders, it never fetches (composables/stores do). *OCP:* new behavior arrives as a new plugin or a new implementation of an existing interface (`IPlugin`, `PaymentPlugin`), never as an `if (provider === 'stripe')` in the host. *LSP:* every `PaymentPlugin` is substitutable — the checkout flow runs against the interface and must not care which provider is behind it. *ISP:* plugins depend on the narrow SDK surfaces they use, not on the whole core. *DIP:* views and plugins depend on core interfaces; concrete clients/stores are injected (provide/inject or factory), never imported deep from another module's internals. |
| **DRY** | A query document, a zod schema, an error-code map, a price formatter exists **once** — in oxid-fe-core if more than one plugin needs it. A second copy is a defect, not a shortcut. Generated GraphQL types are the single source of truth for API shapes; hand-written duplicates of them are forbidden. |
| **Clean code** | Small functions, intention-revealing names, no boolean-flag parameters, no commented-out code, early returns over nesting. Comments state constraints the code cannot show — not what the next line does. ESLint + Prettier + `vue-tsc --noEmit` define "clean enough to commit"; `any` and `@ts-ignore`/`eslint-disable` need a one-line justification at the site and are treated as violations to burn down (see evaluation below). |
| **No overengineering** | Build what the current sprint's acceptance criteria need, nothing speculative: no abstraction with a single implementation unless a second is already named in a sprint, no config switch nobody flips, no premature state library layers. The plugin seams (`IPlugin`, `PaymentPlugin`) are the agreed extension points — everything else stays concrete until a real second case arrives. |
| **No dead code** | Unused exports, unreached branches, orphaned components, stale feature flags and skipped tests do not ship. Enforced, not promised: `knip` (unused files/exports/dependencies) and ESLint `no-unused-vars`/unreachable-code rules run in the quality gate; a skipped test needs a linked ticket or it is deleted. |
| **Regular evaluation of violations** | Violations are visible and reviewed on a cadence, not discovered in archaeology. Each repo keeps `docs/dev_log/<day>/status.md` notes of new suppressions/debt; a **violations report** (lint warnings, type suppressions, knip findings, coverage delta, outdated deps via `npm audit`/`npm outdated`) is generated by one npm script (`npm run evaluate`) and reviewed at every sprint close — the count may only go down or be justified in an ADR/dev_log entry. |
| **Quality guards** | The gate is the same locally and in CI, one source of truth (`docs/quality-gates.md`): `npm run lint` (ESLint+Prettier), `npm run type-check` (`vue-tsc`), `npm test` (Vitest, coverage ≥ 90% in core), `npm run build`, `knip`, Playwright e2e in oxid-fe-user. `./bin/pre-commit-check.sh` runs the full set (mirroring the payment modules' convention); `main` is protected — no merge without the gate green. No commit "to be fixed by the next one". |

## How a sprint uses this

Every sprint doc's acceptance criteria are read **in addition to** this file. A story is "done" when its
tests exist and pass, the quality guards are green, no new dead code or suppressions were added (or they
are justified in the day's dev_log), and the behavior is proven at the outermost layer the story touches
(browser for UI, container for build/tooling).
